Sección 2

¿Qué es una API?

El concepto que conecta el mundo del software. Sin APIs, cada aplicación sería una isla. Con ellas, todo puede hablar con todo.

🔸 API — Application Programming Interface

La interfaz que permite que sistemas se comuniquen

Una API es como un mesero en un restaurante: tú (el cliente) haces un pedido, el mesero (la API) lo lleva a la cocina (el servidor) y te trae la respuesta. No necesitas saber cómo funciona la cocina — solo cómo hacer el pedido correctamente.

// Analogía completa Tu workflow = el cliente que hace el pedido API = el mesero — traduce y entrega Servidor remoto = la cocina — procesa y responde // El "pedido" en términos técnicos: Tu workflow envía: GET https://api.clima.com/bogota Servidor responde: { "temp": 18, "estado": "nublado" }
🌐 REST API — el estándar

La más común

REST (Representational State Transfer) es el estilo de API más usado. Usa HTTP, URLs y JSON. Si una app tiene API pública, casi seguro es REST. Es lo que usarás en n8n el 95% del tiempo.

HTTP nativoJSONURLs claras
📡 Cómo fluye una petición
1. n8n construye la petición método + URL + headers + body 2. La envía al servidor externo → viaja por internet 3. El servidor procesa → autenticación, lógica, datos 4. Responde con JSON + status code 200 OK + { datos } 5. n8n recibe y usa la respuesta

Sección 3

Métodos HTTP

Los cuatro verbos que gobiernan toda comunicación con APIs REST. Cada uno tiene un propósito claro y no son intercambiables.

GET — Obtener datos

Pide datos al servidor sin enviar nada ni modificar nada. Solo lectura. El más simple y más usado.

// Obtener usuario por ID GET https://api.ejemplo.com/usuarios/123 // Obtener lista de productos GET https://api.tienda.com/productos?categoria=ropa // Obtener datos de clima GET https://api.clima.com/ciudad?q=bogota
✅ No envía body · ✅ Params en la URL · ✅ Seguro e idempotente
POST — Enviar datos / Crear

Envía datos al servidor para crear un nuevo recurso o disparar una acción. Es el método de webhooks y formularios.

// Crear un nuevo usuario POST https://api.ejemplo.com/usuarios Body: { "nombre": "Ana García", "email": "ana@email.com" } // Enviar mensaje de Slack POST https://hooks.slack.com/services/xxx Body: { "text": "Hola equipo" }
✅ Body en JSON · ✅ Crea recursos · ⚠️ No idempotente
PUT — Actualizar (reemplazar)

Reemplaza un recurso completo. Envías todos los campos, no solo los que cambian. Si omites un campo, se borra.

// Actualizar usuario completo PUT https://api.ejemplo.com/usuarios/123 Body: { "nombre": "Ana García López", "email": "ana@email.com", "estado": "activo" } // Debes enviar TODOS los campos
⚠️ Reemplaza todo · ✅ Idempotente · ✅ Incluye ID en URL
DELETE + PATCH

DELETE elimina el recurso. PATCH actualiza solo los campos que envías, sin tocar el resto.

// Eliminar usuario DELETE https://api.ejemplo.com/usuarios/123 // Actualizar solo el email (PATCH) PATCH https://api.ejemplo.com/usuarios/123 Body: { "email": "nuevo@email.com" } // Solo cambia email, el resto queda igual
📋 Cuándo usar cada método — regla de oro
Quiero...MétodoBodyEjemplo
Leer / consultar datosGET❌ NoObtener usuario, listar productos
Crear algo nuevoPOST✅ SíCrear lead en CRM, enviar mensaje
Actualizar todo el objetoPUT✅ SíReemplazar configuración completa
Actualizar solo un campoPATCH✅ SíCambiar estado de un pedido
Eliminar un recursoDELETE❌ NoBorrar contacto, cancelar suscripción
Sección 4

JSON — el lenguaje de las APIs

Todo lo que viaja entre sistemas viaja en JSON. Aprende a leerlo, construirlo y acceder a sus datos en n8n con expresiones.

📦 Anatomía del JSON
// JSON = JavaScript Object Notation // Siempre son pares clave: valor { "nombre": "Ana García", ← string (texto) "edad": 28, ← number "activo": true, ← boolean "notas": null, ← null (vacío) "tags": ["vip", "colombia"], ← array "direccion": { ← objeto anidado "ciudad": "Bogotá", "pais": "CO" } }
🔍 Acceder a datos JSON en n8n
// Usando expresiones en cualquier campo // Campo simple {{$json.nombre}} → "Ana García" {{$json.edad}} → 28 // Objeto anidado {{$json.direccion.ciudad}} → "Bogotá" {{$json.direccion.pais}} → "CO" // Array — primer elemento {{$json.tags[0]}} → "vip" {{$json.tags[1]}} → "colombia" // Campo que puede no existir {{$json.telefono ?? 'N/A'}} → "N/A" si no existe
🏗️ Construir JSON para enviar a la API
// En el body del HTTP Request // combinas datos del workflow con valores fijos { "nombre": "{{$json.nombre}}", "email": "{{$json.email}}", "plan": "{{$json.plan ?? 'free'}}", "origen": "n8n-workflow", "timestamp": "{{$now.toISO()}}", "score": {{$json.score}} } // Nota: strings van entre comillas en la expresión // números y booleanos no llevan comillas
📊 JSON de respuesta real — API de pagos
📤 Lo que enviamos (body POST)
{ "nombre": "Ana", "email": "ana@email.com" }
→
📥 Lo que recibimos (respuesta)
{ "status": "ok", "id": "usr_12345", "mensaje": "Usuario creado", "token": "eyJhb..." } // Acceder en nodo siguiente: {{$json.id}} → "usr_12345"
💡
Valida tu JSON antes de enviarlo. Un JSON mal formado (coma extra, comilla faltante) hace fallar el request con un error críptico. Usa jsonlint.com para verificar antes de ejecutar.
Sección 5

Autenticación de APIs

La mayoría de APIs requieren identificarte antes de responder. Aprende los tres métodos más comunes y cómo configurarlos de forma segura en n8n.

🔑 API Key — el más común

Una cadena secreta que la API te da cuando te registras. La incluyes en cada petición para identificarte.

// En el Header (más seguro) Authorization: Bearer sk-abc123xyz X-API-Key: sk-abc123xyz // En la URL (menos seguro, evitar) GET /endpoint?api_key=sk-abc123xyz // En n8n: Authentication → Header Auth // Name: Authorization // Value: Bearer sk-abc123xyz
🎫 Bearer Token — OAuth y JWT

Token temporal obtenido después de autenticarse. Expira y debe renovarse. Lo usan Google, GitHub, Salesforce.

// Header estándar Authorization: Bearer eyJhbGci... // En n8n: usar "Predefined Credential Type" // para servicios populares (Google, GitHub, etc.) // n8n maneja el refresh del token automáticamente // Para OAuth2 manual: // 1. Obtener token con POST /oauth/token // 2. Guardar en variable // 3. Usar en headers de los siguientes requests
🔐 Basic Auth — usuario y contraseña

Combinas usuario:contraseña en Base64 y lo envías en el header. Común en APIs legacy y sistemas internos.

// Header Authorization: Basic dXN1YXJpbzpjb250cmFzZW5h // (Base64 de "usuario:contraseña") // En n8n: Authentication → Basic Auth // Username: tu_usuario // Password: tu_contraseña // n8n hace el encode automáticamente
🛡️ Seguridad — cómo proteger tus API Keys en n8n
// ❌ MAL — API Key hardcodeada en el nodo Authorization: "Bearer sk-abc123xyz789" // Cualquiera que vea el workflow ve la key // ✅ BIEN — Usar Credentials de n8n Credentials → New → HTTP Header Auth Name: Authorization Value: Bearer sk-abc123xyz789 → Guardar como "Mi API Key" // En el nodo HTTP Request: // Authentication → Predefined Credential // Credential: "Mi API Key" // La key queda cifrada, no visible en el workflow // ✅ MUY BIEN — Variables de entorno Authorization: "Bearer {{$env.MI_API_KEY}}" // La key vive fuera del workflow
Sección 6

Nodo HTTP Request

El nodo más versátil de n8n. Un solo nodo para hablar con cualquier API del mundo. Aquí está todo lo que necesitas saber para configurarlo correctamente.

⚙️ Anatomía del nodo HTTP Request en n8n
// Campos del nodo — de arriba a abajo Method: GET | POST | PUT | PATCH | DELETE URL: https://api.ejemplo.com/endpoint Authentication: None | Basic | Header | OAuth2 Headers: Content-Type: application/json Authorization: Bearer {{token}} Query Params: ?page=1&limit=10 Body: { "campo": "{{$json.valor}}" } Options: Timeout: 30000 ms Retry on Fail: 3 intentos Response Format: JSON | Text | Binary
🏗️ Ejemplo real — llamar a la API de OpenAI
POST https://api.openai.com/v1/chat/completions
// Headers Authorization: Bearer {{$env.OPENAI_KEY}} Content-Type: application/json // Body { "model": "gpt-4o-mini", "messages": [{ "role": "user", "content": "Clasifica este lead: {{$json.interes}}" }], "max_tokens": 100 } // Respuesta → acceder con: {{$json.choices[0].message.content}}
🏗️ Ejemplo real — llamar a la API de WhatsApp
POST https://graph.facebook.com/v18.0/{{phone_id}}/messages
// Headers Authorization: Bearer {{$env.WA_TOKEN}} Content-Type: application/json // Body { "messaging_product": "whatsapp", "to": "{{$json.telefono}}", "type": "text", "text": { "body": "Hola {{$json.nombre}}" } } // Respuesta exitosa: { "messages": [{ "id": "wamid.xxx" }] }

Sección 7

Status Codes y Errores

La API siempre responde con un código. Ese código te dice si todo fue bien, si cometiste un error o si el servidor falló. Ignorarlos es construir castillos en el aire.

📋 Los códigos más importantes
200 OK 201 Created 204 No Content

✅ Todo salió bien. 200 = éxito con datos. 201 = recurso creado. 204 = éxito sin datos que devolver.

400 Bad Request 401 Unauthorized

⚠️ Error tuyo. 400 = datos mal formados o faltantes. 401 = no estás autenticado o tu API Key es incorrecta.

403 Forbidden 404 Not Found 429 Too Many

⚠️ Error tuyo. 403 = autenticado pero sin permiso. 404 = el recurso no existe. 429 = demasiadas peticiones (rate limit).

500 Server Error 502 Bad Gateway 503 Unavailable

🔴 Error del servidor. No es tuyo. Usar retry automático — generalmente es temporal.

🛡️ Manejo de errores en n8n
// Opción 1: Continue on Error // El workflow no se detiene si la API falla HTTP Request (Continue on Error: ON) ↓ éxito: datos normales ↓ error: { error: "...", statusCode: 404 } ↓ IF $json.error no vacío: → notificar fallo + log // Opción 2: Retry on Fail // n8n reintenta automáticamente Options → Retry on Fail: ON Max tries: 3 Wait Between: 5000 ms // Opción 3: verificar status code IF $response.statusCode >= 400: → manejar el error específico → 401: renovar token y reintentar → 429: esperar y reintentar → 500: usar ruta alternativa
⚠️ Los 5 errores más comunes al usar APIs
  • ✗
    URL incorrecta — un typo, una barra extra o un dominio mal escrito → 404. Siempre copia la URL de la documentación oficial, nunca la escribas a mano.
  • ✗
    Método HTTP equivocado — usar GET cuando la API espera POST → 405 Method Not Allowed. Lee la documentación para saber qué método acepta cada endpoint.
  • ✗
    Headers mal configurados — olvidar Content-Type: application/json cuando envías un body → 400. Casi toda API REST lo necesita en POST/PUT/PATCH.
  • ✗
    No entender la estructura del JSON — intentar acceder a $json.nombre cuando la respuesta tiene $json.data.user.name. Inspecciona siempre la respuesta real antes de mapear.
  • ✗
    Ignorar errores de respuesta — asumir que 200 siempre llega y no manejar el 400 o 500. Un workflow robusto siempre verifica el status code.
Sección 8

Ejercicio Paso a Paso

Construir un flujo completo: recibir datos, enviarlos a una API, procesar la respuesta y actuar según el resultado.

🚀 Caso práctico — Integración con API externa

Recibir un usuario → enviarlo a una API → procesar la respuesta → notificar resultado

Usaremos JSONPlaceholder (sin API Key) como API de práctica. Luego el mismo patrón aplica a cualquier API real.

🌐 JSONPlaceholder Sin API Key Mismo patrón para APIs reales
📌 Los 9 pasos para construir el flujo
  • 1

    Crear el workflow en n8n

    Nuevo workflow → nombrar "Clase 7 — APIs". Activa "Save on Execute" para no perder el progreso entre pruebas.

    New Workflow → nombrar
  • 2

    Agregar trigger — Manual o Webhook

    Para practicar: Manual Trigger. Para producción: Webhook POST. El Manual Trigger te permite ejecutar con un clic sin necesidad de enviar datos desde fuera.

    + → Manual Trigger
  • 3

    Preparar datos con nodo Set

    Agrega los datos que vas a enviar a la API. En el Set define: nombre, email y cualquier dato necesario para el body del request.

    nombre → "Ana García" email → "ana@email.com" titulo → "Prueba de API" cuerpo → "Datos enviados desde n8n"
  • 4

    Añadir nodo HTTP Request

    Agrega el nodo HTTP Request después del Set. Este nodo es el que habla con la API.

    + → HTTP Request
  • 5

    Configurar el método HTTP

    Para crear un recurso usamos POST. Si fuera consultar datos sería GET. Selecciona el método correcto en el dropdown del nodo.

    Method: POST
  • 6

    Definir la URL del endpoint

    La URL de la API a la que te conectas. Para la práctica usamos JSONPlaceholder.

    URL: https://jsonplaceholder.typicode.com/posts // Para una API real, copiar de su documentación
  • 7

    Agregar headers y body

    Configura el Content-Type y construye el body con los datos del Set usando expresiones {{$json.campo}}.

    Header: Content-Type: application/json Body: { "title": "{{$json.titulo}}", "body": "{{$json.cuerpo}}", "userId": 1 }
  • 8

    Ejecutar el flujo y revisar la respuesta

    Clic en "Execute Workflow". Abre el nodo HTTP Request y revisa la pestaña "Output". Deberías ver el JSON de respuesta con el recurso creado.

    // Respuesta esperada de JSONPlaceholder: { "id": 101, "title": "Prueba de API", "userId":1 }
  • 9

    Usar la respuesta — Set + Notificación

    Después del HTTP Request, agrega un Set para extraer el ID recibido, y luego un nodo de notificación que use esos datos.

    // Set después del HTTP Request id_creado → {{$json.id}} mensaje → "Recurso #{{$json.id}} creado en la API" estado → "{{$json.id ? 'exitoso' : 'error'}}"
    Set → Gmail / Slack / log

Sección 9

Entregable, Buenas Prácticas y Bonus

Lo que debes entregar, los errores que debes evitar y los próximos pasos para ir más allá de las APIs básicas.

✅ Entregable — flujo que consume una API
  • ✓
    Consume una API externa con HTTP Request
    El nodo HTTP Request hace una petición real a una URL externa y recibe respuesta.
  • ✓
    Envía y/o recibe datos en JSON
    El body del request usa datos dinámicos del workflow con expresiones. La respuesta se parsea correctamente.
  • ✓
    Procesa la respuesta de la API
    Los datos de la respuesta (ID, status, mensaje) se extraen y usan en los nodos siguientes.
  • ✓
    Manejo básico de errores
    El flujo usa Continue on Error o Retry, y hay una rama que maneja el caso de fallo.
  • ✓
    API Key / auth protegida
    Si la API requiere autenticación, la credencial está en Credentials de n8n, no hardcodeada.
  • ✓
    Probado con datos reales
    Al menos 2 ejecuciones exitosas verificadas: una con datos válidos y una para ver qué pasa con error 4xx.
🧪 Buenas prácticas al trabajar con APIs
  • ✓
    Leer la documentación antes de construir
    Cada API es distinta. La documentación te dice exactamente qué método, qué URL, qué headers y qué body necesitas. 5 minutos leyendo docs ahorran horas de depuración.
  • ✓
    Probar en Postman o Insomnia primero
    Antes de construir el nodo en n8n, prueba el request manualmente en Postman. Si funciona ahí, es más fácil replicarlo en n8n.
  • ✓
    Inspeccionar la respuesta real antes de mapear
    Ejecuta el flujo una vez y abre el output del HTTP Request. Mira exactamente cómo viene estructurado el JSON para saber cómo acceder a cada campo.
  • ✓
    Validar el status code siempre
    Un status 200 significa éxito. Un 201 significa creado. Un 400+ significa error. Actúa diferente según el código, no asumas que siempre llegará 200.
🚀 Bonus nivel pro
🔐
OAuth2 completo: flujo de autenticación de dos pasos: obtener token con POST + usarlo en requests posteriores. Necesario para Google, Salesforce, HubSpot.
🔗
Encadenar múltiples APIs: resultado de API 1 → input de API 2. Ejemplo: geocodificar con Google Maps → calcular ruta con HERE Maps.
🔄
Transformación avanzada de datos: usar Function para reestructurar la respuesta compleja de una API antes de usarla en el siguiente paso.
🌐
Crear tu propia API con webhooks: usar n8n como backend: el webhook de n8n actúa como endpoint de tu API, procesa y responde con Respond to Webhook.
