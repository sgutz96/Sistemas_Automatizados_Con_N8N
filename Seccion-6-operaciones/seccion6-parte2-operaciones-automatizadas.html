Operaciones Automatizadas

Automatizar una tarea es útil. Automatizar un proceso completo es transformador. Esta clase construye sistemas que reciben una solicitud, deciden qué hacer y ejecutan sin intervención humana de principio a fin.

🔥 El salto de esta clase
Antes — Automatizaciones parciales
"Automatizar partes"

Un webhook guarda datos. Otro envía un email. Pero alguien tiene que leer el email, decidir qué hacer y ejecutar la siguiente acción manualmente. El humano sigue en el loop.

Ahora — Operaciones end-to-end
"Automatizar el proceso completo"

La solicitud llega → el sistema la entiende → decide la ruta → ejecuta todas las acciones → registra el resultado. Sin intervención humana en ningún punto del flujo.

E2E

🧠 Qué vas a aprender en esta clase
  • ✓
    Automatización de procesos internos completos
    No solo notificaciones o guardado de datos. Flujos que leen una solicitud, la entienden, toman una decisión y ejecutan la cadena de acciones correcta.
  • ✓
    Clasificación automática con Switch multi-ruta
    Un solo nodo Switch que enruta solicitudes de soporte, ventas, facturación, información y escalados por caminos completamente distintos.
  • ✓
    Sistema de prioridades automático
    Detectar urgencia según palabras clave, tipo de cliente o SLA. Alta prioridad activa el equipo en 15 minutos; baja prioridad entra a la cola estándar.
  • ✓
    Registro de resultados y manejo de errores
    Cada solicitud procesada queda registrada con timestamp, acción tomada y resultado. Los errores no detienen el flujo: se capturan, se registran y se notifican.
  • ✓
    Reintentos automáticos y fallbacks
    Si una acción falla (el email no sale, la API no responde), el sistema reintenta antes de escalar a revisión manual. Los flujos frágiles no sirven en producción.
Sección 2

Conceptos Clave

Tres ideas que definen cómo funcionan los sistemas de operaciones automatizadas y por qué son cualitativamente distintos a un workflow de captura de datos.

🔸 Operaciones — procesos internos del negocio

Todo lo que el equipo hace de forma repetitiva es candidato a automatizar

Las "operaciones" son los procesos que mantienen funcionando el negocio: responder solicitudes de soporte, asignar tareas al equipo correcto, actualizar estados en el CRM, enviar facturas, escalar incidencias. Todos tienen algo en común: siguen reglas predecibles.

🎧
Soporte al cliente
Clasificar, asignar, responder y escalar tickets automáticamente
💼
Ventas internas
Procesar solicitudes, actualizar pipeline, notificar al equipo
🧾
Operaciones financieras
Verificar pagos, emitir facturas, actualizar cuentas
🔸 Lógica condicional en operaciones

El mismo IF/Switch que aprendiste antes, ahora aplicado a procesos de negocio reales. La pregunta no es "¿tiene teléfono?" sino "¿cuál es el tipo de solicitud?"

// Decisiones típicas en operaciones si tipo = "soporte" → asignar al equipo de soporte → crear ticket en el sistema → confirmar recepción al usuario si tipo = "ventas" → notificar al equipo comercial → actualizar pipeline en CRM → enviar propuesta automática si tipo = "facturacion" → verificar datos fiscales → generar factura → enviar por email si no → escalar a revisión manual
🔸 Automatización end-to-end — la diferencia real

End-to-end significa que el sistema completa el proceso sin que nadie tenga que intervenir en ningún punto. El humano solo aparece cuando el sistema explícitamente lo decide (escalado).

ParcialEnd-to-end
Recibe solicitudRecibe + clasifica
Envía emailClasifica + decide + actúa
Alguien lee y actúaActúa automáticamente
Resultado manualRegistra + confirma solo
Sin manejo de errorError → reintento → fallback
💡
La regla del proceso automatizable: si una persona puede describir en 5 pasos o menos lo que hace cada vez que llega una solicitud, ese proceso se puede automatizar. El workflow replica exactamente esos 5 pasos. Si la descripción necesita más de 5 pasos, empieza por los primeros 3 y agrega el resto progresivamente.

Paso 1 de 4

Clasificación — Entender la Solicitud

Antes de enrutar, el sistema necesita entender qué llegó. Este paso limpia los datos, valida la solicitud y enriquece el payload con todo lo que los nodos siguientes van a necesitar.

⚙️ Nodo Code — procesar y enriquecer la solicitud
// Nodo: Code — procesamiento inicial const d = $input.first().json; // ── PASO 1: NORMALIZAR CAMPOS ───────────────────── const tipo = (d.tipo || '').toLowerCase().trim(); const mensaje = (d.mensaje || '').trim(); const email = (d.email || '').toLowerCase().trim(); const nombre = (d.nombre || 'Cliente').trim(); // ── PASO 2: VALIDAR CAMPOS OBLIGATORIOS ─────────── const errores = []; if (!email || !/^[^@]+@[^@]+\.[^@]+$/.test(email)) errores.push('email_invalido'); if (!tipo) errores.push('tipo_faltante'); if (!mensaje || mensaje.length < 5) errores.push('mensaje_vacio'); // ── PASO 3: TIPOS VÁLIDOS ───────────────────────── const tiposValidos = ['soporte','ventas','facturacion','informacion','escalado']; const tipoFinal = tiposValidos.includes(tipo) ? tipo : 'desconocido'; // ── PASO 4: METADATOS ───────────────────────────── const esClientePremium = ['premium','enterprise'].includes(d.plan); const timestamp = new Date().toISOString(); const solicitudId = `SOL-${Date.now()}`; return [{ json: { ...d, tipo: tipoFinal, email, nombre, mensaje, errores, es_valida: errores.length === 0, es_premium: esClientePremium, timestamp, solicitud_id: solicitudId }}];

La rama "información" es la más valiosa a largo plazo. Con el tiempo, el 60–70% de las solicitudes suelen ser preguntas que ya tienen respuesta. Automatizar completamente esa rama libera al equipo para las solicitudes que realmente necesitan atención humana.
Paso 3 de 4

Sistema de Prioridades Automático

No todas las solicitudes son igual de urgentes. El sistema detecta la prioridad según múltiples señales y actúa diferente: la prioridad alta activa al equipo en minutos; la baja entra a la cola estándar.

🎯 Nodo Code — calcular prioridad automáticamente
// Nodo: Code — motor de prioridades const d = $input.first().json; let puntos = 0; const razones = []; const msg = (d.mensaje || '').toLowerCase(); // ── SEÑALES DE URGENCIA EN EL MENSAJE ──────────── const palabrasUrgentes = ['urgente','crítico','no funciona', 'caído','perdí acceso','bloqueado','emergencia']; const palabrasAltas = ['problema','error','falla','no puedo']; if (palabrasUrgentes.some(p => msg.includes(p))) { puntos += 50; razones.push('palabra_urgente'); } if (palabrasAltas.some(p => msg.includes(p))) { puntos += 25; razones.push('palabra_alta'); } // ── TIPO DE CLIENTE ─────────────────────────────── if (d.plan === 'enterprise') { puntos += 40; razones.push('enterprise'); } if (d.plan === 'premium') { puntos += 20; razones.push('premium'); } // ── TIPO DE SOLICITUD ───────────────────────────── if (d.tipo === 'escalado') { puntos += 60; razones.push('tipo_escalado'); } if (d.tipo === 'soporte') { puntos += 15; razones.push('tipo_soporte'); } // ── CLASIFICAR ──────────────────────────────────── const prioridad = puntos >= 60 ? 'alta' : puntos >= 30 ? 'media' : 'baja'; // SLA según prioridad (en minutos) const sla = { alta: 15, media: 120, baja: 480 }[prioridad]; return [{ json: { ...d, prioridad, puntos_prioridad: puntos, razones_prioridad: razones.join(', '), sla_minutos: sla }}];

Paso 4 de 4

Registro de Resultados y Manejo de Errores

El sistema no está completo sin un registro de todo lo que procesa y sin un plan para cuando algo sale mal. Los errores son inevitables en producción; la diferencia está en cómo los manejas.

💾 Registro en Google Sheets — al final de cada rama
// Nodo: Code — preparar registro final // Se ejecuta al final de TODAS las ramas antes de Sheets const d = $input.first().json; return [{ json: { // ── IDENTIFICACIÓN ────────────────────────────── solicitud_id: d.solicitud_id, timestamp: d.timestamp, timestamp_fin: new Date().toISOString(), // ── DATOS DEL SOLICITANTE ─────────────────────── nombre: d.nombre, email: d.email, plan: d.plan || 'free', // ── CLASIFICACIÓN ─────────────────────────────── tipo: d.tipo, prioridad: d.prioridad, puntos: d.puntos_prioridad, // ── RESULTADO ─────────────────────────────────── ruta_tomada: d.ruta_tomada || d.tipo, acciones: d.acciones_realizadas || 'completadas', estado: 'procesado', sla_minutos: d.sla_minutos, // ── MENSAJE (para referencia) ─────────────────── mensaje: d.mensaje.slice(0, 200) }}];
⚠️ Manejo de errores — el nodo Error Trigger
// Workflow separado: manejador de errores // Trigger: Error Trigger (se activa si algún // nodo falla en el workflow principal) Nodo 1: Error Trigger // Recibe: nombre del workflow, nombre del nodo, // mensaje de error y los datos que fallaron Nodo 2: Code — extraer info del error const err = $input.first().json; return [{ json: { workflow: err.workflow.name, nodo: err.execution.lastNodeExecuted, mensaje: err.execution.error.message, datos: JSON.stringify(err.execution.data) .slice(0,500) }}] Nodo 3: Slack → canal #errores-automatizacion Nodo 4: Sheets → hoja "Errores" → registrar

Sección 8

Buenas Prácticas y Errores Comunes

Los sistemas de operaciones tienen que funcionar en producción, bajo carga real, con datos sucios y con el equipo dependiendo de ellos. Estos son los principios que los hacen robustos.

✅ Buenas prácticas
  • ✓
    Mantener la lógica clara y documentada
    Nombra cada nodo con su función exacta: "Code — calcular prioridad", "IF — validar email", "Switch — enrutar por tipo". En 3 meses, tú mismo no recordarás qué hace "Function 4".
  • ✓
    Nombrar bien todas las ramas del Switch
    En el campo "Output Name" del Switch, escribe el nombre del caso: "soporte", "ventas", "escalado". Hace el diagrama legible de un vistazo.
  • ✓
    Probar todos los casos posibles
    Crea un dataset de prueba con una solicitud por cada tipo y por cada nivel de prioridad. 15 casos mínimo. Ejecuta cada uno y verifica que la ruta y el registro son correctos.
  • ✓
    Registrar siempre el resultado
    Cada rama termina en el nodo de registro de Sheets. Sin excepción. Incluso los fallbacks y los errores se registran. Un sistema sin log no existe en producción.
  • ✓
    Evitar complejidad innecesaria
    Si el workflow tiene más de 40 nodos, divídelo en sub-workflows. n8n permite llamar a otros workflows como si fueran funciones. Un workflow por proceso, no un megaworkflow que hace todo.
⚠️ Errores comunes
  • ✗
    Condiciones mal configuradas sin prueba
    Un Switch con la regla tipo = "Soporte" (con mayúscula) no captura las solicitudes con tipo = "soporte" (minúscula). Siempre normaliza a minúsculas en el nodo Code antes del Switch.
  • ✗
    No cubrir todos los casos con fallback
    Un tipo de solicitud que nadie anticipó llega y el dato se pierde sin ruido. El fallback es la red de seguridad; siempre actívalo y conéctalo a un registro de "casos no cubiertos" para mejorar el sistema.
  • ✗
    Flujos difíciles de entender (spaghetti)
    Conexiones que cruzan el canvas en todas direcciones, nodos sin nombrar, lógica mezclada con acciones. Organiza de izquierda a derecha, agrupa por función, y usa colores de nodo para diferenciar etapas.
  • ✗
    No manejar errores de las APIs externas
    La API de tu CRM puede estar caída 5 minutos. Si no tienes Error Trigger + reintento, esas solicitudes se pierden para siempre. Configura el Error Trigger en un workflow separado para todos tus workflows de producción.
🚀 Bonus nivel pro — extensiones del sistema
🔗
Múltiples condiciones encadenadas: después del Switch de tipo, cada rama tiene su propio IF de prioridad. El soporte urgente de un cliente enterprise activa una ruta completamente distinta al soporte estándar de un cliente free.
🤖
Clasificación automática con IA: en vez de reglas basadas en palabras clave, enviar el campo "mensaje" a Claude API y pedir que devuelva el tipo y la prioridad. La IA entiende el contexto mejor que cualquier regex.
🔁
Sub-workflows reutilizables: el bloque de "enviar confirmación al usuario" es el mismo en todas las ramas. Conviértelo en un sub-workflow y llámalo desde cada rama. Si cambias el template, cambia en todos los lugares a la vez.
📊
Dashboard de operaciones: una hoja de Sheets con fórmulas que muestran solicitudes por tipo, por prioridad, tiempo promedio de resolución y tasa de error. Actualizado en tiempo real por el workflow.
⏰
SLA enforcement automático: después de crear cada solicitud, lanzar un workflow paralelo con Wait del SLA correspondiente. Si al volver el estado sigue siendo "sin_atender", escalar automáticamente sin que nadie tenga que monitorear.
🔌
Integraciones con herramientas internas: conectar directamente con Jira (tickets de soporte), HubSpot (oportunidades de ventas) o QuickBooks (facturación) vía sus nodos nativos de n8n o el nodo HTTP Request.
Sección 9

Entregable — Sistema de Operaciones

Lo que debe estar funcionando al terminar la clase. Un sistema que recibe solicitudes, decide qué hacer y las procesa de principio a fin sin intervención humana.

✅ Checklist del entregable
  • ✓
    Webhook activo recibiendo solicitudes
    El endpoint acepta el JSON con campos tipo, mensaje, nombre, email y plan. Devuelve 200 con el ID de la solicitud creada.
  • ✓
    Nodo Code normalizando y validando
    Solicitudes con email inválido van a la hoja "Errores" y no continúan. Solicitudes válidas tienen el campo es_valida: true, solicitud_id y timestamp.
  • ✓
    Sistema de prioridades funcionando
    Una solicitud con la palabra "urgente" de un cliente premium tiene prioridad alta. Una consulta de información estándar tiene prioridad baja. El campo prioridad es correcto en ambos casos.
  • ✓
    Switch con 5 ramas + fallback conectadas
    Cada tipo de solicitud va por su output. Una solicitud de tipo "soporte" llega al canal #soporte de Slack. Una de "escalado" notifica directamente al responsable.
  • ✓
    Email de confirmación enviado al usuario
    El solicitante recibe un email con el ID de solicitud y el tiempo estimado de respuesta según la prioridad calculada.
  • ✓
    Registro en Sheets completo
    Después de cada solicitud procesada, aparece una fila nueva en la hoja "Solicitudes" con todos los campos: ID, tipo, prioridad, ruta, estado y timestamp.
  • ✓
    Probado con 6 solicitudes de prueba
    Una por cada tipo (soporte, ventas, facturación, información, escalado) más una con datos inválidos. Todos van por la ruta correcta y quedan registrados.
🏆 De automatización simple a orquestación de operaciones
  • ①

    Captura y guardado

    Webhook → validar → guardar en Sheets → notificar. Un proceso lineal, siempre igual.

  • ②

    Seguimiento con estados

    Emails automáticos, delays, actualización de estado. El workflow actúa en el tiempo.

  • ③

    Decisiones con lógica condicional

    IF y Switch dividen el flujo. Cada caso recibe un trato distinto. El sistema empieza a "pensar".

  • ④

    Orquestación de operaciones end-to-end

    Validación → clasificación → prioridades → múltiples ramas → acciones específicas → registro → manejo de errores. Un proceso completo sin intervención humana.
