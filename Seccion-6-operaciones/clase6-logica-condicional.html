Clase 6

Automatizaciones con Lógica Condicional

Hasta ahora tus workflows hacen siempre lo mismo sin importar qué datos llegan. A partir de esta clase, el sistema lee los datos y decide qué hacer. Eso lo convierte en inteligente.

🔥 El salto de esta clase
Clases 1–5 — Workflows lineales
"Hacer siempre lo mismo"

Llega un dato → siempre el mismo email → siempre el mismo estado → siempre la misma notificación. Sin importar quién es el lead ni qué quiere.

Clase 6 — Workflows condicionales
"Decidir según los datos"

Llega un dato → el sistema evalúa → toma el camino correcto → ejecuta la acción exacta para ese caso. Cada lead recibe un trato diferente.

IF
nodo para dos caminos: sí o no
Switch
nodo para múltiples rutas según valor
AND/OR
combinar condiciones en una sola regla
∞
condiciones anidadas sin límite
🧠 Qué vas a aprender en esta clase
  • ✓
    El nodo IF — bifurcar en dos caminos
    La estructura más básica de la lógica: si se cumple una condición, ejecuta el camino A; si no, el camino B. Se usa en el 80% de los workflows reales.
  • ✓
    El nodo Switch — múltiples rutas desde un solo punto
    Cuando hay más de dos casos posibles, el Switch evalúa un campo y envía el dato por la salida que corresponde. Hasta 10 salidas distintas desde un solo nodo.
  • ✓
    Condiciones AND / OR — combinar reglas
    Una condición puede depender de varios campos a la vez. "Si el email existe Y el score es mayor a 70" es una condición AND. Aprenderás a combinarlas correctamente.
  • ✓
    Condiciones sobre texto, números y fechas
    Los operadores disponibles en n8n: igual, contiene, empieza con, mayor que, menor que, existe, está vacío. Cada tipo de dato tiene sus operadores específicos.
  • ✓
    Caso práctico: router de leads inteligente
    Combinarás IF y Switch para construir un sistema que enruta cada lead por la ruta exacta según su perfil, interés, hora y estado previo.
Sección 2

Conceptos Clave

La lógica condicional es el mismo concepto en programación, en Excel y en n8n. Si ya usaste un IF en Excel, ya sabes lo más importante.

🔸 ¿Qué es la lógica condicional?

Una instrucción que evalúa algo y actúa diferente según el resultado

En lenguaje humano: "Si el lead tiene teléfono, llámale. Si no, solo envíale email." En n8n eso es exactamente un nodo IF. La condición es la pregunta; las dos salidas son las respuestas.

Lenguaje humano
Si el lead tiene más de 80 puntos...
  → asignar al vendedor senior
Si no...
  → asignar al equipo general
→
n8n — Nodo IF
Campo: score Operador: mayor que Valor: 80 ✓ True → asignar senior ✗ False → equipo general

🔸 AND vs OR

Cuando necesitas evaluar más de una condición a la vez.

AND — ambas deben cumplirse
score > 70
Y
telefono existe
→ solo si las DOS son true
OR — basta con una
fuente = "referido"
O
score > 90
→ si CUALQUIERA es true
🔸 IF vs Switch — cuándo usar cada uno
Nodo IF — usa cuando…
La respuesta solo puede ser sí o no. ¿Tiene teléfono? ¿El score es alto? ¿El email es válido? Dos salidas: True / False.
Nodo Switch — usa cuando…
Hay tres o más casos distintos. ¿Qué plan eligió? ¿De qué país viene? ¿Cuál es su industria? Cada valor tiene su propia salida.
💡
La regla de oro: usa IF cuando la pregunta tenga respuesta binaria (sí/no, verdadero/falso, mayor/menor). Usa Switch cuando el campo evaluado pueda tener múltiples valores distintos con acciones distintas para cada uno. Mezclarlos mal es el error más común.
Sección 3

Nodo IF — Dos Caminos

El nodo IF es el más usado en n8n. Evalúa una o más condiciones y divide el flujo en dos ramas: True (se cumple) y False (no se cumple). Todo lo que entra, sale por uno de los dos lados.

🔀 Estructura del nodo IF en n8n
Configuración en el editor
// Nodo: IF // Modo: Rules (recomendado) // ── CONDICIÓN SIMPLE ────────────────────── Value 1: {{$json.score}} Operation: Larger Than Value 2: 80 // Resultado: ✓ Output 0 (True) → score mayor a 80 ✗ Output 1 (False) → score 80 o menos // ── CONDICIÓN CON EXPRESIÓN ─────────────── // También puedes usar JavaScript: Value 1: {{$json.email && $json.telefono}} Operation: Is True // True solo si AMBOS campos existen

✅ IF con condiciones AND — ejemplo real
// Nodo IF — modo: Rules // Combinar con AND (todas deben cumplirse) // Condición 1 Value 1: {{$json.score}} Operation: Larger Than Value 2: 70 // Condición 2 (clic en "+ Add Condition") Value 1: {{$json.telefono}} Operation: Is Not Empty // Combinar con: AND // True solo si score > 70 Y tiene teléfono // → llamada directa al lead // False: solo email, sin llamada
✅ IF con condiciones OR — ejemplo real
// Nodo IF — modo: Rules // Combinar con OR (basta una) // Condición 1 Value 1: {{$json.fuente}} Operation: Equals Value 2: "referido" // Condición 2 Value 1: {{$json.score}} Operation: Larger Than Value 2: 90 // Combinar con: OR // True si es referido O si el score > 90 // → tratamiento VIP automático // False: flujo estándar
⚠️
Las dos salidas del IF siempre deben estar conectadas. Si dejas la salida False sin conectar, los datos que no cumplan la condición simplemente desaparecen del workflow. Conecta siempre ambas salidas, aunque una de ellas vaya a un nodo que no hace nada (NoOp) para que sea explícito.
Sección 4

Nodo Switch — Múltiples Rutas

El Switch es como tener varios IFs en un solo nodo. Evalúa un campo y enruta el dato por la salida que corresponda. Es la herramienta perfecta cuando hay más de dos casos posibles.

🔢 Estructura del nodo Switch
Switch — campo evaluado: {{$json.plan}}
1
plan = "premium"
→ Onboarding personal + llamada de bienvenida + descuento VIP
2
plan = "pro"
→ Email de activación + tutorial en video + soporte por chat
3
plan = "basico"
→ Email automático + acceso al portal de autoservicio
FB
Fallback — ninguna regla coincidió
→ Notificar al equipo para revisión manual
⚙️ Configuración del Switch en n8n
// Nodo: Switch Mode: Rules ← recomendado // ── REGLA 1 ─────────────────────────────── Value 1: {{$json.plan}} Operation: Equals Value 2: "premium" Output: 0 // ── REGLA 2 ─────────────────────────────── Value 1: {{$json.plan}} Operation: Equals Value 2: "pro" Output: 1 // ── REGLA 3 ─────────────────────────────── Value 1: {{$json.plan}} Operation: Equals Value 2: "basico" Output: 2 // ── FALLBACK ────────────────────────────── Fallback Output: activado → Output 3 // Siempre activar el fallback

🔀 Switch en modo Expression — evaluación dinámica
// Nodo Switch — modo: Expression (avanzado) // Útil cuando la condición es un cálculo, no un valor fijo Mode: Expression // Expresión que devuelve un número de output: Output: {{ $json.score >= 80 ? 0 : // Output 0: caliente $json.score >= 50 ? 1 : // Output 1: medio $json.score >= 30 ? 2 : // Output 2: frío 3 // Output 3: descartar }} // Ventaja: una sola expresión define todas las rutas // Desventaja: más difícil de leer para el equipo // Recomendado: usar Rules para la mayoría de casos
💡
Siempre activa el Fallback Output. Si llega un lead con un valor de plan que no estaba en tus reglas (por ejemplo "enterprise" que no definiste), sin fallback el dato se pierde silenciosamente. Con fallback va a un camino de revisión manual y no se pierde.
⚠️
El Switch no conecta la misma salida dos veces. Cada output es independiente. Si quieres que dos valores distintos ejecuten la misma acción, conecta ambos outputs al mismo nodo siguiente, o fusiona las ramas con un nodo Merge después.
Sección 5

Condiciones Avanzadas

Más allá del "igual a" y "mayor que". Estas son las condiciones que resuelven los casos reales: campos vacíos, textos parciales, fechas relativas y evaluaciones sobre arrays.

🔍 Condiciones sobre texto — operadores clave
// ── CONTIENE (Contains) ─────────────────── campo: {{$json.email}} op: Contains valor: "empresa.com" // True para ana@empresa.com, carlos@empresa.com // ── NO CONTIENE (Does Not Contain) ──────── campo: {{$json.email}} op: Does Not Contain valor: "gmail" // True para todos los NO gmail → B2B // ── VACÍO / NO VACÍO ────────────────────── campo: {{$json.telefono}} op: Is Empty ← o Is Not Empty // True si el campo es "", null o undefined // ── EXPRESIÓN REGEX (avanzado) ──────────── campo: {{$json.email}} op: Regex valor: "^[^@]+@[^@]+\.[^@]+$" // Valida formato de email básico
🔢 Condiciones sobre números — rangos y comparaciones
// ── MAYOR / MENOR ───────────────────────── campo: {{$json.score}} op: Larger Than valor: 80 // ── ENTRE (Between) — en Expression mode ── campo: {{$json.score >= 50 && $json.score < 80}} op: Is True // Score entre 50 y 79 inclusive // ── DIVISIBLE (par/impar para distribución) campo: {{$json.id % 2}} op: Equals valor: 0 // IDs pares → vendedor A, impares → vendedor B // Útil para distribución Round Robin sin base de datos
📅 Condiciones sobre fechas y tiempo — casos reales
// ── HORARIO LABORAL ─────────────────────── // Enviar emails solo de lunes a viernes 9–18h campo: {{new Date().getHours()}} op: Larger Than Or Equal valor: 9 // Y también: campo: {{new Date().getHours()}} op: Smaller Than valor: 18 // Combinar con AND → ambas true = horario laboral
// ── DÍAS SIN ACTIVIDAD ──────────────────── // ¿Llevan más de 7 días sin responder? campo: {{ const ultimo = new Date($json.ultimo_contacto); const hoy = new Date(); const dias = (hoy - ultimo) / (1000*60*60*24); dias }} op: Larger Than valor: 7 // True si llevan más de 7 días sin actividad // → activar campaña de reactivación automática

Sección 6

Combinaciones Reales

En la práctica, IF y Switch casi nunca se usan solos. Esta sección muestra los patrones más útiles de cómo combinarlos para resolver casos del mundo real.

🧩 Patrón 2 — Merge + IF: reagrupar ramas y tomar decisión unificada

A veces quieres que varias ramas del Switch vuelvan a juntarse antes de continuar. El nodo Merge une los datos y luego un IF decide el siguiente paso para todos.

// Escenario: 3 planes distintos con onboarding diferente, // pero todos pasan por la misma verificación de email al final // Switch → 3 ramas (premium, pro, básico) // Cada rama hace su onboarding específico // Las 3 ramas convergen en un Nodo Merge // El Merge reúne todos los datos // Nodo Merge — configuración: Mode: Append ← todos los items juntos Number of Inputs: 3 // Después del Merge → IF: ¿email corporativo? campo: {{$json.email}} op: Does Not Contain valor: "gmail" // True → notificar al equipo B2B // False → email al equipo B2C
🧩 Patrón 3 — IF como guardián: validar antes de ejecutar

Uno de los usos más valiosos del IF es como guardián: evitar que el workflow continúe con datos incorrectos o incompletos antes de llamar a una API o actualizar una base de datos.

// IF como guardián de email válido campo: {{$json.email}} op: Regex valor: "^[^@]+@[^@]+\.[^@]+$" ✓ True → continuar al siguiente nodo ✗ False → guardar en hoja "Leads con error" + notificar al equipo // Nunca enviará un email a una dirección // inválida porque el IF lo bloquea antes
// IF como guardián de duplicados // (después de buscar en Sheets) campo: {{$json.ya_existe}} op: Is False ← o Equals false ✓ True → es nuevo → continuar flujo completo ✗ False → ya existe → solo actualizar fecha de último contacto // Evita crear registros duplicados en Sheets // y enviar emails de bienvenida dos veces
Sección 7

Caso Práctico — Router de Leads Inteligente

Construyes un workflow completo que recibe un lead y lo enruta por el camino exacto según su perfil. Este es el tipo de sistema que los equipos comerciales pagan miles de dólares en plataformas externas.

🚀 El objetivo del ejercicio

Cuando llega un lead, el sistema debe:

  • 1
    Validar que tiene email válido
    Si no es válido → guardar en hoja de errores y parar.
  • 2
    Verificar si ya existe en la base
    Si ya existe → solo actualizar fecha. Si es nuevo → continuar.
  • 3
    Calcular su segmento
    VIP, caliente, medio o frío según score y fuente.
  • 4
    Enrutar por el camino correcto
    Cada segmento tiene una acción distinta.
  • 5
    Verificar el horario antes de notificar
    Si es fuera de horario → encolar para el día siguiente.
  • 6
    Enviar el email correcto según el segmento
    4 templates distintos, uno por segmento.
  • 7
    Actualizar estado en Sheets
    El registro siempre refleja la acción más reciente.
  • 8
    Notificar solo si es urgente
    VIP y caliente → Slack. Medio y frío → solo email.
⚙️ Código completo del router — Nodo Code principal
// Nodo: Code — Router de leads completo const d = $input.first().json; // ── PASO 1: VALIDAR EMAIL ───────────────────────── const emailValido = /^[^@]+@[^@]+\.[^@]+$/.test(d.email); if (!emailValido) { return [{ json: { ...d, error: 'email_invalido', accion: 'descartar' } }]; } // ── PASO 2: DETECTAR TIPO DE EMAIL ─────────────── const emailsCorporativos = ['gmail','hotmail','yahoo','outlook']; const esB2B = !emailsCorporativos.some(dom => d.email.toLowerCase().includes(dom) ); // ── PASO 3: CALCULAR SEGMENTO ───────────────────── let segmento; if (d.score >= 80 && d.fuente === 'referido') segmento = 'vip'; else if(d.score >= 80) segmento = 'caliente'; else if(d.score >= 50) segmento = 'medio'; else segmento = 'frio'; // ── PASO 4: VERIFICAR HORARIO LABORAL ──────────── const hora = new Date().getHours(); const dia = new Date().getDay(); // 0=dom, 6=sab const horaLaboral = hora >= 9 && hora < 18 && dia > 0 && dia < 6; // ── PASO 5: DEFINIR ACCIÓN SEGÚN SEGMENTO ──────── const config = { vip: { notificar: true, canal: '#ventas-vip', urgente: true }, caliente: { notificar: true, canal: '#ventas-urgente', urgente: true }, medio: { notificar: false, canal: '#ventas-general', urgente: false }, frio: { notificar: false, canal: '', urgente: false } }[segmento]; return [{ json: { ...d, segmento, es_b2b: esB2B, hora_laboral: horaLaboral, notificar: config.notificar, canal_slack: config.canal, urgente: config.urgente, email_template: `template_${segmento}` }}];
🔢 Switch sobre el segmento calculado
// Nodo: Switch — después del Code Mode: Rules Campo: {{$json.segmento}} // Regla 1 Equals "vip" → Output 0 // Acciones VIP: // - Email personalizado // - Slack #ventas-vip // - Tarea urgente en Calendar // - Asignar director comercial // Regla 2 Equals "caliente" → Output 1 // Acciones caliente: // - Email rápido // - Slack #ventas-urgente // - Tarea en 2h // Regla 3 Equals "medio" → Output 2 // Acciones medio: // - Email estándar // - Tarea en 24h // Fallback → Output 3 (frío → nurture)
✅ IF de horario — antes de notificar por Slack
// Nodo: IF — solo notificar en horario laboral // Va ANTES del nodo de Slack en cada rama Value 1: {{$json.hora_laboral}} Operation: Is True ✓ True → Enviar Slack inmediatamente ✗ False → Guardar en cola de "pendientes" que se envía al inicio del día siguiente (cron 9am que lee la cola y envía todo) // Así el equipo no recibe notificaciones // a las 2am por leads de otras zonas horarias

Sección 8

Buenas Prácticas y Errores Comunes

La lógica condicional es donde los workflows se rompen con más frecuencia. Estos son los patrones que hacen la diferencia entre un sistema frágil y uno que funciona en producción.

✅ Buenas prácticas
  • ✓
    Calcular variables de decisión en un Code previo
    No pongas lógica compleja dentro del IF. Calcula el campo segmento, prioridad o ruta en un nodo Code antes, y que el IF o Switch solo evalúe ese campo simple.
  • ✓
    Siempre conectar la salida False del IF
    Aunque no hagas nada con los datos que no cumplen la condición, conéctalos a un nodo de log o de notificación. Nunca dejes datos desapareciendo silenciosamente.
  • ✓
    Siempre activar el Fallback del Switch
    Los valores inesperados siempre aparecen en producción. El fallback los captura antes de que causen un error silencioso en el sistema.
  • ✓
    Nombrar los nodos con claridad
    "IF — ¿score alto?" es mucho mejor que "IF1". Cuando el workflow tenga 30 nodos, los nombres son la única documentación que tienes.
  • ✓
    Probar cada rama individualmente
    Usa el botón "Execute" con datos de prueba específicos para cada caso. Un lead con score 90, otro con 60, otro con 20. Verifica que cada uno va por la rama correcta.
⚠️ Errores comunes
  • ✗
    Comparar tipos distintos
    score como string vs como número: "80" > 80 da un resultado inesperado en JavaScript. Usa Number($json.score) para asegurarte de comparar números con números.
  • ✗
    Condición sobre campo que puede ser null
    $json.telefono.length > 7 lanza un error si telefono es null. Usa siempre $json.telefono?.length > 7 o verifica existencia primero.
  • ✗
    Usar OR cuando se necesita AND (y viceversa)
    Confundir AND con OR en condiciones múltiples es el error más frecuente. Léelo en voz alta: "¿necesito que TODAS se cumplan, o basta con UNA?"
  • ✗
    Switch sin fallback en producción
    Un valor nuevo (como un plan que se agregó después) hace que los datos desaparezcan sin error. Siempre activa el fallback y conéctalo a una notificación de revisión.
  • ✗
    Más de 4 niveles de IFs anidados
    El workflow se vuelve ilegible y difícil de depurar. Cuando necesites más de 3 niveles, refactoriza: usa un Code que calcule la decisión y un Switch limpio sobre el resultado.
🚀 Bonus nivel pro — extensiones avanzadas
🧠
Lógica condicional con IA: en vez de reglas fijas, enviar el contenido del lead a Claude via API y pedirle que decida la ruta óptima. La IA puede evaluar el texto libre del campo "mensaje" y detectar intención de compra.
📊
A/B testing automático: usar Math.random() > 0.5 como condición en un IF para dividir leads al 50% entre dos variantes de email. Medir tasas de apertura en Sheets y ajustar.
🕐
Routing por timezone: detectar la zona horaria del lead por su dominio o código de país y enrutar a un equipo diferente para que siempre lo atienda alguien en su horario laboral.
🔁
Re-routing dinámico: un workflow separado que corre cada noche y re-evalúa todos los leads "medio" con actividad reciente para ver si subieron de segmento y merecen acción inmediata.
⚡
Condicionales sobre historial: buscar en Sheets si el email ya tuvo interacciones previas y usar ese historial como variable de decisión. Un lead que ya habló antes merece un trato diferente.
🛡️
Guardianes en cadena: poner 3–4 IFs al inicio del workflow (email válido, no duplicado, no en lista negra, no bot) antes de ejecutar ninguna acción real. El workflow es así a prueba de datos sucios.

    Nodo IF de validación funcionando
