Outputs y Resultados

El final inteligente de un workflow. No se trata solo de terminar — se trata de terminar bien: respondiendo, registrando, notificando y dejando todo en orden.

🎯 La pregunta que cierra cada workflow

"¿Qué sabe el mundo cuando este workflow termina?"

Un workflow sin output claro es trabajo invisible. El cliente no sabe si su pedido fue confirmado. El sistema origen no sabe si la operación fue exitosa. El equipo no tiene registro de lo que pasó. Los outputs son la prueba de que la automatización funcionó.

Output 1 de 7

Respond to Webhook

Cuando el flujo empieza con un Webhook, el sistema que lo llamó espera una respuesta. El nodo "Respond to Webhook" le devuelve exactamente lo que necesita.

↩️
Respond to Webhook · Respuesta HTTP al origen
Cierra el ciclo HTTP con el sistema que llamó
Cuando un formulario, una app o un sistema externo hace un POST al webhook de n8n, espera una respuesta HTTP. Sin el nodo "Respond to Webhook", la petición queda abierta hasta que n8n la cierra con un 200 automático. Con el nodo, tú controlas exactamente qué se responde, con qué código HTTP y con qué datos.
↩️ HTTP 200 / 400 / 500 📦 Body JSON ⚡ Respuesta inmediata 🔗 Cierra el loop HTTP 🛡️ Código de error controlado
⚙️ Configuración del nodo
// Respuesta exitosa — 200 OK Status Code: 200 Response Body: { "success": true, "message": "Lead recibido correctamente", "id": "{{$json.id_crm}}", "timestamp":"{{$now}}" } // Respuesta de error controlado — 400 Status Code: 400 Response Body: { "success": false, "error": "Email inválido o faltante", "code": "INVALID_EMAIL" }
📌 Cuándo y dónde colocarlo
✅
Siempre que el trigger sea Webhook — el sistema origen espera confirmación de recepción
✅
APIs que construyes en n8n — n8n como backend: recibe petición, procesa, responde JSON
✅
Formularios con validación — responder con éxito o con mensaje de error específico al front-end
⚠️
Colocarlo temprano si el flujo es largo — responder primero al webhook y luego procesar en paralelo, evitando timeouts
❌
No necesario en Schedule o Manual — solo aplica cuando el trigger es HTTP
🏗️ Patrón: responder rápido y procesar después
// Problema: el flujo tarda 10 segundos → timeout del cliente // Solución: separar respuesta de procesamiento WEBHOOK recibe pedido ↓ Set → validar datos básicos ↓ Respond to Webhook ← responder en <200ms { "success": true, "message": "Pedido recibido, procesando..." } ↓ (el workflow sigue ejecutándose en segundo plano) HTTP Request → ERP ↓ Gmail → cliente ↓ Sheets → registrar // El cliente ya recibió confirmación. // El procesamiento ocurre independientemente.
💡
Códigos HTTP que debes conocer: 200 OK, 201 Created (nuevo recurso), 400 Bad Request (datos inválidos), 401 Unauthorized, 404 Not Found, 500 Server Error. Usar el código correcto permite que el sistema origen reaccione apropiadamente.
⚠️
Timeout: por defecto muchos sistemas esperan respuesta en 5-30 segundos. Si tu flujo es largo, coloca el "Respond to Webhook" antes de los pasos lentos y continúa procesando después.
Output 2 de 7

Logs y Registros

La memoria del workflow. Todo lo que ejecuta n8n debe dejar rastro: qué pasó, cuándo, con qué datos y con qué resultado. Sin logs, no hay trazabilidad.

📋
Logs · Trazabilidad · Auditoría
Todo workflow debe dejar rastro
Un log es el registro de lo que ocurrió. En n8n tienes dos niveles: el log interno que n8n guarda automáticamente en el historial de ejecuciones, y el log externo que tú construyes explícitamente en Sheets, una base de datos o un sistema de observabilidad. El segundo es el que importa en producción.
📊 Google Sheets como log 🗄️ DB de logs ⏱️ Timestamp siempre ✅ / ❌ Estado del resultado 🔍 Auditoría completa
⚙️ Estructura de un buen log
// Columnas mínimas de un log en Sheets o DB timestamp → "{{$now}}" workflow → "Procesar-Lead" evento → "lead_recibido" estado → "exitoso" o "fallido" id_item → "{{$json.id}}" datos_clave → "{{$json.email}}" mensaje → "Lead creado en CRM: clt_8f3a" duracion_ms → "{{$execution.resumeUrl}}" // Columnas extra para errores error_msg → "{{$json.error ?? ''}}" nodo_fallo → "HTTP Request - CRM" reintento → 2
📌 Los 3 momentos de log en un workflow
1

Al recibir el input

Registrar que llegó la petición, qué datos trajo, de qué fuente. Sirve para auditar si el dato llegó y cómo llegó.

evento: "recibido"
2

Si ocurre un error

Registrar qué nodo falló, el mensaje de error, los datos del item afectado. Esencial para diagnóstico.

evento: "error" + detalle
3

Al completar exitosamente

Registrar el resultado final, IDs generados, acciones tomadas. La confirmación de que todo funcionó.

evento: "completado" + resultado
🏢 Log en Sheets vs Log en base de datos
CriterioGoogle SheetsBase de datos
VolumenHasta ~10k filas cómodamenteMillones sin problema
VisibilidadTodo el equipo lo ve y filtraRequiere query o panel
Velocidad setup5 minutos30-60 minutos
BúsquedaFiltros de SheetsSQL completo con índices
Mejor paraEquipos no técnicos, <1k eventos/díaProducción real, +1k eventos/día
💡
Regla del log: el log no es opcional en producción. Si el workflow falla a las 3am y nadie lo vio, sin log no sabrás qué pasó, a quién afectó ni cuántos items se perdieron. Sheets + log estructurado es el mínimo aceptable.
Output 3 de 7

Notificaciones Finales

El output más visible. La confirmación que el usuario recibe, el resumen que llega al equipo, la alerta que cierra el ciclo entre la automatización y las personas.

🔔
Notificación de cierre · Confirmación al usuario y equipo
El mundo sabe que el workflow terminó
La notificación final no es lo mismo que la acción del flujo. La acción es lo que hace el workflow. La notificación de cierre es la confirmación de que todo salió bien — o mal. Va dirigida a dos audiencias distintas: el usuario final que inició el proceso y el equipo interno que debe saberlo.
👤 Confirmación al usuario 👥 Resumen al equipo ✅ Éxito / ❌ Fallo 📧 Email · 💬 Slack · ✈️ Telegram
⚙️ Dos audiencias, dos mensajes distintos
// Para el USUARIO FINAL (cliente) → Canal: Email o WhatsApp → Tono: claro, tranquilizador, humano → Contenido: qué pasó con SU operación Email para el cliente: "Hola {{nombre}}, Tu pedido #{{id}} fue confirmado ✅ Llegará el {{fecha_entrega}}. Puedes rastrearlo aquí: {{link}}" ──────────────────────────────── // Para el EQUIPO INTERNO → Canal: Slack o Telegram → Tono: técnico, datos concretos → Contenido: métricas de la ejecución Slack #operaciones: "✅ Pedido procesado Cliente: {{nombre}} ({{email}}) Monto: ${{monto}} COP Guía: {{num_guia}} Tiempo: {{duracion}}ms"
📌 Cuándo notificar y cuándo no
✅
Siempre al usuario final en transacciones — pedidos, pagos, registros. Necesita saber que funcionó
✅
Siempre al equipo en eventos de negocio importantes — nuevo cliente, deal cerrado, incidente
✅
Siempre cuando el flujo falla — equipo debe saber qué se rompió y cuándo
❌
No notificar en cada ejecución de flujos que corren 100 veces al día — generas ruido y se ignoran
⚠️
Agrupa notificaciones frecuentes en un resumen diario en vez de mensajes individuales
🏗️ Patrón: notificación diferenciada por resultado
// El flujo termina con IF para personalizar la notificación ...proceso principal... ↓ IF resultado == "exitoso" → TRUE: Gmail cliente: "✅ Tu operación fue exitosa" Slack equipo: "✅ Procesado: {{nombre}} - ${{monto}}" Sheets log: estado = "completado" → FALSE: Gmail cliente: "⚠️ Hubo un problema, te contactamos" Slack equipo: "🚨 FALLO: {{nombre}} - Error: {{msg}}" Sheets log: estado = "fallido" + detalle_error // Ambas ramas notifican — nadie se queda sin respuesta
Output 4 de 7

Feedback al Sistema

El output que actualiza el origen. Después de procesar, el workflow regresa al sistema que disparó el evento para actualizarlo: cambiar el estado, marcar como procesado, agregar datos.

🔄
Feedback · Update · Marcar como procesado
Cierra el ciclo con el sistema origen
Muchos workflows leen datos de un sistema, los procesan y deben volver a ese mismo sistema para actualizar el estado. Ejemplo: leer un pedido de Airtable, procesarlo, y actualizar la columna "estado" de ese mismo registro a "enviado". Sin feedback, el sistema origen cree que el item sigue pendiente.
✏️ Actualizar estado 🏷️ Marcar como procesado 🔗 Volver al origen 📊 Sheets · Airtable · CRM · DB ♻️ Evitar reprocesamiento
⚙️ Patrón: leer → procesar → actualizar
// Flujo: procesar leads pendientes de Sheets Schedule cada hora ↓ Sheets READ: obtener filas donde estado == "pendiente" ↓ Filter: solo items con email válido ↓ Loop por cada lead ↓ HTTP → crear en CRM → si OK: Sheets UPDATE fila: estado = "procesado" id_crm = "{{$json.crm_id}}" fecha_ok = "{{$now}}" → si ERROR: Sheets UPDATE fila: estado = "error" msg_error = "{{$json.error}}" intentos = {{$json.intentos + 1}} // La próxima ejecución NO reprocesa los "procesado" // Solo vuelve a intentar los "error"
🏢 Casos reales de feedback
📦
ERP de pedidos: después de generar guía → actualizar campo "estado_envío" y "num_guía" en el pedido original del ERP
🎫
Sistema de tickets: después de resolver → cambiar estado de "abierto" a "resuelto" + agregar nota con el resultado
📋
Airtable de tareas: workflow completa una tarea → marca el checkbox "Hecho" y agrega fecha de completado
👤
CRM de leads: después de enviar email de bienvenida → actualizar etapa del lead de "nuevo" a "contactado"
💳
Sistema de pagos: pago validado → marcar factura como "pagada" en el sistema contable con fecha y referencia
⚠️ Por qué el feedback es crítico — el problema del doble procesamiento
// Sin feedback: reprocesamiento infinito Ejecución 1 → lee pedido "pendiente" → procesa → NO actualiza origen Ejecución 2 → lee MISMO pedido "pendiente" → procesa OTRA VEZ Ejecución 3 → lee MISMO pedido "pendiente" → el cliente recibe 3 emails // Con feedback: cada item se procesa exactamente una vez Ejecución 1 → lee pedido "pendiente" → procesa → actualiza a "procesado" Ejecución 2 → lee pedidos "pendiente" → este ya no aparece → omitido Ejecución 3 → igual → 0 reprocesos, 0 duplicados
Output 5 de 7

Detener el Flujo

A veces el mejor output es no hacer nada más. Saber cuándo y cómo detener el workflow correctamente evita errores, datos duplicados y acciones no deseadas.

🛑
Stop · No-Op · Early exit · Detención controlada
Parar el flujo intencionalmente, no por error
Hay situaciones en las que el workflow debe detenerse sin ejecutar las acciones principales: datos inválidos, item duplicado, condición no cumplida. Detener el flujo correctamente es distinto a que falle — es una decisión consciente que no genera alertas de error pero sí puede dejar un registro.
🚫 Filter vacío ↩️ Respond 400 temprano 🔇 Sin acción = detención 🏷️ Log silencioso ✅ Detención limpia
⚙️ Las 3 formas de detener el flujo
// Forma 1: Filter que no deja pasar nada Filter: email contiene "@" → Si ningún item pasa → flujo se detiene solo → n8n marca la ejecución como exitosa (0 items) // Forma 2: IF sin rama false conectada IF condicion_critica == true → true: continúa con las acciones → false: sin nodo conectado → se detiene // Forma 3: Respond al webhook + no continuar IF dato_duplicado == true → true: Respond to Webhook: { "msg": "Duplicado ignorado", status: 200 } ← no hay más nodos después → false: continúa el flujo normal
📌 Cuándo detener el flujo voluntariamente
🔁
Item duplicado: el mismo webhook llega dos veces (reintentos) — procesar una sola vez y descartar el segundo
📭
Sin datos relevantes: el Schedule corrió pero no hay nuevos registros que procesar — salida limpia sin errores
⛔
Condición de negocio no cumplida: el pedido fue cancelado antes de que el workflow lo procesara — detener sin enviar nada
🧪
Datos de prueba: detectar emails con "test" o "example.com" y descartarlos sin llegar a las acciones reales
🏗️ Patrón: idempotencia — procesar una sola vez aunque llegue dos veces
// El webhook de Stripe puede llegar duplicado (reintentos automáticos) // Solución: verificar antes de actuar WEBHOOK recibe pago de Stripe ↓ HTTP Request: buscar en DB si pago_id ya existe ↓ IF registro_encontrado == true → true (duplicado): Respond to Webhook: { "msg": "already processed" } Sheets log: "Duplicado ignorado: {{pago_id}}" ← workflow termina aquí, sin reenviar email → false (nuevo): Continuar → activar cuenta → email → log → respond // Resultado: cada pago se procesa exactamente una vez
Output 6 de 7

Retorno al Sub-workflow

Cuando un workflow hijo termina, le devuelve datos al padre. Así los sub-workflows no son cajas negras — son funciones con entrada y salida definida.

📤
Respond to Parent Workflow · Output estructurado
El sub-workflow responde con datos al flujo padre
Cuando usas "Execute Workflow" para llamar a un sub-workflow, el flujo padre puede esperar una respuesta. El sub-workflow usa el nodo "Respond to Parent Workflow" para devolver datos estructurados — resultado de la operación, IDs generados, estado, errores — que el flujo padre puede usar en sus siguientes pasos.
📥 Padre espera respuesta 📤 Hijo devuelve JSON ✅ Estado de la operación 🆔 IDs generados 🔗 Composición de workflows
⚙️ Flujo padre ↔ hijo con retorno de datos
// ── WORKFLOW PADRE: "Procesar Lead" ────────────── Webhook → Set → Filter ↓ Execute Workflow: "Crear-en-CRM" pasa: { nombre, email, telefono, empresa } espera respuesta: true ↓ recibe del hijo: { "crm_id": "clt_8f3a9b", "estado": "creado", "etapa": "lead" } ↓ Set: combinar datos originales + respuesta del CRM ↓ Gmail: "Bienvenido {{nombre}}, tu ID es {{crm_id}}" Slack: "Lead creado: {{nombre}} → {{crm_id}}" // ── SUB-WORKFLOW HIJO: "Crear-en-CRM" ──────────── When Called By Another Workflow recibe: { nombre, email, telefono } ↓ HTTP Request → POST al CRM API ↓ Respond to Parent Workflow: { "crm_id": "{{$json.id}}", "estado": "creado", "etapa": "lead" }
💡 Qué debe retornar un sub-workflow
  • ✓
    Estado de la operación — "exitoso" / "fallido" para que el padre decida qué hacer
  • ✓
    IDs generados — si se creó un registro, el ID del nuevo objeto para usarlo en pasos siguientes
  • ✓
    Mensaje legible — descripción del resultado para log o notificación
  • ✓
    Datos mínimos — solo lo que el padre necesita, no todo el JSON interno del sub-workflow
  • ✗
    No retornar nada — si el padre no recibe respuesta, no puede actuar según el resultado
🏗️ Ventajas del retorno estructurado
🔗
Composición limpia: el padre orquesta, el hijo ejecuta. Cada uno hace lo suyo y se comunican por interfaz definida
🧪
Testing independiente: puedes probar el sub-workflow solo, verificar que retorna el JSON correcto antes de integrarlo
♻️
Reutilización real: el mismo sub-workflow lo llaman múltiples flujos padres y todos reciben el mismo formato de respuesta
🛡️
Manejo de errores limpio: el hijo retorna estado: "error" y el padre decide si reintenta, notifica o sigue
Output 7 de 7

Output de Resumen

Cuando el workflow procesa múltiples items, el output final consolida todo: cuántos fueron exitosos, cuántos fallaron, métricas del proceso, listo para reportar.

📊
Summary Output · Consolidación de resultados
Un resumen al final de procesar N items
Cuando un workflow procesa 50 leads, envía 200 emails o sincroniza 1000 registros, el output no puede ser 1000 notificaciones individuales. El output de resumen consolida todos los resultados en un solo mensaje: X procesados, Y exitosos, Z fallidos, duración total. Un solo Slack o email que lo dice todo.
🔢 Contador de resultados ✅ Exitosos / ❌ Fallidos ⏱️ Duración total 📋 Lista de errores 📧 Un solo mensaje final
⚙️ Construir el resumen con Function
// Después del Loop, todos los resultados llegan al Function // Cada item del loop pasó su resultado: {ok: true/false, email, error?} const items = $input.all(); const exitosos = items.filter(i => i.json.ok === true); const fallidos = items.filter(i => i.json.ok === false); const errores = fallidos.map(i => `• ${i.json.email}: ${i.json.error}` ).join('\n'); return [{ json: { total: items.length, exitosos: exitosos.length, fallidos: fallidos.length, tasa_exito: `${(exitosos.length/items.length*100).toFixed(1)}%`, lista_errores: errores || "Ninguno", timestamp: $now.toISO() } }];
📧 El mensaje de resumen final
// Slack — resumen del proceso batch "📊 *Proceso completado* — {{$now.toFormat('dd/MM HH:mm')}} ✅ Exitosos: {{exitosos}} / {{total}} ❌ Fallidos: {{fallidos}} / {{total}} 📈 Éxito: {{tasa_exito}} {{#if fallidos > 0}} ⚠️ *Errores:* {{lista_errores}} {{/if}}" // Email — reporte al gerente "Asunto: Proceso de emails completado Se procesaron {{total}} registros: - Exitosos: {{exitosos}} - Fallidos: {{fallidos}} - Tasa de éxito: {{tasa_exito}} Ver log completo: [link a Sheets]"
🏢 Casos reales de output resumen
📧
Campaña de email: después de enviar 500 emails → resumen: 498 enviados, 2 fallidos (emails inválidos)
💳
Cobros recurrentes: 200 intentos de cobro → 185 exitosos, 15 fallidos → lista de clientes a contactar manualmente
🔄
Sincronización diaria: 1000 registros sincronizados entre sistemas → resumen: cuántos nuevos, actualizados, sin cambios, errores
📊
Reporte batch: generación de 50 reportes PDF para clientes → cuántos generados, cuántos con error, tiempo total
