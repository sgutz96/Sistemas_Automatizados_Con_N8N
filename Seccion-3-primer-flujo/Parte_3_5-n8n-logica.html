Lógica en n8n

La lógica es lo que convierte un workflow lineal en una automatización inteligente. Toma decisiones, filtra datos, maneja errores y se adapta a cada situación.

🧠 La diferencia entre un workflow básico y uno profesional

Un workflow sin lógica hace siempre lo mismo. Con lógica, actúa diferente según la situación.

Básico: recibe datos → envía email. Siempre igual, sin importar qué. Con lógica: recibe datos → valida → si es cliente VIP hace una cosa, si no otra → si falla reintenta → registra el resultado. Eso es un workflow real.

Lógica 1 de 8

IF Avanzado

Más allá del simple sí/no. Condiciones múltiples con AND y OR, IFs anidados, comparaciones complejas y lógica que cubre todos los casos posibles.

🔀
IF · Condicional avanzado
Condiciones combinadas y anidadas
En la Parte 3 viste el IF básico. Ahora profundizamos: múltiples condiciones con AND/OR, cómo anidar IFs para crear árbol de decisión complejo, condiciones sobre arrays, fechas, y cómo evitar los patrones que rompen workflows en producción.
AND · OR 🌲 IF anidado 📅 Comparar fechas 📋 Comparar arrays 🔢 Rangos numéricos
⚙️ AND — todas deben cumplirse
// Lead calificado = email válido // AND monto > umbral AND país correcto email contiene "@" AND monto > 500000 AND pais igual a "CO" → TRUE: lead calificado → CRM premium → FALSE: lead genérico → CRM estándar // Caso de stock crítico stock < 10 AND activo igual a true AND categoria igual a "A" → alerta urgente al equipo de compras
⚙️ OR — basta con una
// Notificar si es de LATAM pais igual a "CO" OR pais igual a "MX" OR pais igual a "AR" → TRUE si es de alguno de los tres países // Escalar ticket si es urgente o VIP prioridad igual a "alta" OR tipo_cliente igual a "enterprise" → TRUE en cualquiera de los dos casos
🌲 IFs anidados — árbol de decisión completo
// Nivel 1: ¿el pago fue aprobado? IF estado_pago == "aprobado" // Nivel 2 (true): ¿es cliente nuevo? IF es_nuevo == true → Email bienvenida + onboarding ELSE → Email confirmación de renovación ELSE // Nivel 2 (false): ¿fue rechazado o pendiente? IF estado_pago == "rechazado" → Email "tarjeta rechazada" + link de reintento ELSE → Email "pago pendiente, verificando..."

En n8n: IF nivel 1 → rama true → IF nivel 2 → dos ramas. Rama false → otro IF → dos ramas →

💡
Regla de oro: si necesitas más de 3 niveles de IF anidados, es señal de que debes usar un Switch o mover la lógica a un nodo Function con JavaScript. Los IFs profundos son imposibles de mantener.
⚠️
Rama false vacía: si la rama false de un IF no tiene nodo conectado, n8n la descarta silenciosamente. Siempre conecta las dos ramas, aunque la false sea solo un nodo de log o notificación.

Switch Avanzado

Enrutamiento inteligente con múltiples salidas. Casos de uso complejos, salida "fallback" para lo inesperado, y combinación con otros nodos.

🎛️
Switch · Enrutamiento múltiple avanzado
Hasta N salidas con lógica compleja por ruta
El Switch no solo evalúa igualdad exacta. Puedes configurar cada salida con condiciones distintas: una con rango numérico, otra con texto que contiene, otra con fecha comparada. Y siempre con una salida "default" que captura lo que no encaja en ninguna regla.
🛣️ N salidas 📋 Condición por salida 🪤 Fallback default 🔢 Rangos y texto ⚡ Sin IFs anidados
⚙️ Switch con condiciones distintas por salida
// Clasificar el tamaño del pedido // Cada salida tiene su propia condición Salida 0 — "Pequeño": monto > 0 AND monto <= 99999 Salida 1 — "Mediano": monto > 99999 AND monto <= 499999 Salida 2 — "Grande": monto > 499999 AND monto <= 1999999 Salida 3 — "Enterprise": monto > 1999999 Fallback — default: cualquier cosa que no encajó // Cada salida conecta a su propio flujo: → Pequeño : proceso estándar → email simple → Mediano : asignar vendedor → llamada de seguimiento → Grande : alertar gerencia → propuesta personalizada → Enterprise: CEO notificado → reunión agendada → Fallback : log de anomalía → revisión manual
🏢 Casos reales de Switch complejo
🌍
Por región + idioma: CO/MX → español LATAM, ES → español EU, US → inglés, resto → inglés genérico
🎫
Categoría de soporte: "facturación" → equipo finanzas, "técnico" → dev, "envíos" → logística, otros → primer nivel
💳
Estado de pago: "aprobado", "rechazado", "pendiente", "reembolsado" → cada uno con su flujo propio
📦
Tipo de envío: "nacional", "bogotá mismo día", "internacional" → cada uno con tarifa, transportadora y tiempo distintos
🪤 La salida Fallback — por qué es obligatoria
// Sin fallback: Switch recibe estado = "cancelado" → No encaja en ninguna salida → Item desaparecido silenciosamente → Nadie se entera del problema // Con fallback: Switch recibe estado = "cancelado" → Va a salida default → Log en Sheets: "estado desconocido" → Slack alerta: "revisar manualmente" → El dato no se pierde

Regla: todo Switch en producción debe tener un fallback conectado a una notificación de anomalía.

Lógica 3 de 8

Nodo Filter

El guardián del workflow. Descarta items que no cumplen condiciones antes de que lleguen a los nodos costosos. Simple, silencioso y muy poderoso.

🧹
Filter · Descarte de items
Solo pasan los datos que importan
El nodo Filter evalúa cada item de la lista y solo deja pasar los que cumplen la condición. Los que no la cumplen son descartados sin generar errores ni ruido. A diferencia del IF (que bifurca), el Filter simplemente limpia. Perfecto antes de un Loop o una acción costosa.
✅ Pasan: cumplen 🗑️ Descartan: no cumplen 🔇 Sin error ni ruido 📋 Funciona en arrays ⚡ Antes de acciones costosas
⚙️ Filter vs IF — diferencia clave
// IF — bifurca en dos ramas Items → IF condición → rama TRUE: items que cumplen → rama FALSE: items que NO cumplen // Necesitas manejar ambas ramas ───────────────────────────── // Filter — solo pasan los que cumplen Items → Filter condición → solo items que cumplen → los demás desaparecen sin ruido // Una sola salida, más limpio
📌 Cuándo usar Filter
✅
Antes de un Loop — filtrar la lista para solo iterar los items relevantes
✅
Limpiar datos inválidos — descartar emails sin @, nombres vacíos, montos en 0
✅
Antes de API costosa — solo llamar la API con los items que realmente necesitan procesarse
✅
Fechas — solo procesar registros del día de hoy, no todos los históricos
❌
No usar si necesitas hacer algo con los items descartados — ahí sí necesitas IF
🏢 Ejemplos reales de Filter en acción
// 1. Filtrar solo leads con email válido Filter: email contiene "@" AND email no contiene "test" → Solo pasan emails reales de personas // 2. Filtrar pedidos de hoy para reporte diario Filter: fecha_creacion es hoy AND estado igual a "completado" → Solo pedidos completados hoy // 3. Filtrar clientes activos con saldo Filter: activo igual a true AND saldo_pendiente > 0 → Solo clientes que deben dinero y siguen activos // 4. Filtrar noticias no procesadas en RSS Filter: procesado no igual a true AND categoria igual a "tech" → Solo noticias tech que aún no se han publicado

Expresiones en n8n

La lógica que vive dentro de los campos. Con expresiones puedes calcular, transformar, condicionar y manipular datos directamente en cualquier nodo, sin código aparte.

✏️
Expresiones · Lógica inline en campos
JavaScript ligero dentro de {{ }}
Las expresiones son mini-scripts JavaScript que escribes directamente en cualquier campo de n8n entre dobles llaves. No necesitas un nodo Function separado para operaciones simples: transformar texto, calcular fechas, hacer condicionales ternarios, acceder a datos de otros nodos.
{{ $json.campo }} Ternario if/else 📅 Fechas con $now 🔢 Cálculos 📡 $node acceso cruzado
⚙️ Las expresiones más usadas
// ─── ACCESO A DATOS ─────────────────────────────── {{$json.nombre}} dato del nodo actual {{$json.direccion.ciudad}} dato anidado {{$json.items[0].precio}} primer elemento del array // ─── FECHAS ─────────────────────────────────────── {{$now}} timestamp actual (ISO) {{$now.toFormat('dd/MM/yyyy')}} fecha formateada {{$now.plus({days: 7})}} fecha en 7 días {{$now.minus({days: 30})}} hace 30 días // ─── TEXTO ──────────────────────────────────────── {{$json.nombre.toUpperCase()}} MAYÚSCULAS {{$json.email.toLowerCase()}} minúsculas {{$json.descripcion.slice(0, 100)}} primeros 100 caracteres {{$json.nombre.trim()}} quitar espacios // ─── CÁLCULOS ───────────────────────────────────── {{$json.precio * $json.cantidad}} total del item {{Math.round($json.monto * 1.19)}} monto con IVA {{($json.ventas / $json.meta * 100).toFixed(1)}}% % de meta // ─── CONDICIONAL TERNARIO ───────────────────────── {{$json.vip === true ? "Cliente VIP" : "Cliente estándar"}} {{$json.monto > 500000 ? "grande" : "pequeño"}} {{$json.email ? $json.email : "sin-email@n8n.io"}} fallback // ─── ACCEDER A OTRO NODO ────────────────────────── {{$node["Nodo Set"].json.campo}} dato de nodo anterior {{$("Webhook").first().json.email}} dato del trigger
🏢 Expresiones en contexto real
// Campo "asunto" del email "Pedido #{{$json.id}} - {{$json.estado === 'aprobado' ? '✅ Confirmado' : '⚠️ Pendiente revisión'}}" // Campo "cuerpo" del Slack "{{$json.nombre}} acaba de {{$json.es_nuevo ? 'registrarse 🎉' : 'renovar su plan 🔄' }}\nMonto: ${{ ($json.monto/1000).toFixed(0) }}k COP" // Campo "fecha_entrega" en Sheets {{$now.plus({days: $json.tipo === 'express' ? 1 : 3}).toFormat('dd/MM/yyyy')}}
⚠️ Errores comunes con expresiones
  • ✗
    Acceder a campo que no existe
    Si $json.telefono no existe, la expresión falla. Usa: {{$json.telefono ?? "N/A"}}
  • ✗
    Olvidar las dobles llaves
    Escribir $json.nombre sin {{ }} → texto literal, no evalúa
  • ✗
    Anidar demasiado en una sola expresión
    Si es complejo → moverlo a un nodo Function. Las expresiones son para lógica simple
  • ✓
    Usa el editor de expresiones
    n8n tiene un editor visual con preview en tiempo real. Siempre úsalo para validar antes de guardar

Manejo de Errores

La diferencia entre un workflow de prueba y uno de producción. Todo lo que puede fallar, fallará. La pregunta es si tu workflow lo maneja con gracia o se rompe sin avisar.

🛡️
Error handling · Producción real
Workflows que fallan bien
Un workflow sin manejo de errores es una bomba de tiempo. La API externa puede caer, los datos pueden llegar mal formados, una credencial puede expirar. n8n tiene múltiples herramientas para capturar errores, tomar rutas alternativas, reintentar y notificar sin detener todo el flujo.
🪤 Error Trigger 🔁 Auto-retry 🛤️ Ruta alternativa 📩 Notificar al fallar 📋 Log de errores
⚙️ Error Trigger — workflow de manejo de errores
// Workflow principal: "Procesar Pagos" Webhook → Set → HTTP API pago → Gmail // Si el nodo HTTP falla → n8n puede disparar // el workflow de errores automáticamente // Workflow secundario: "Handler de Errores" Error Trigger ↓ recibe: { workflow: "Procesar Pagos", node: "HTTP Request", error: "Connection timeout", data: { ...datos del item que falló } } ↓ Set → construir mensaje de alerta ↓ Slack: "🚨 Falló workflow Procesar Pagos Nodo: HTTP Request Error: Connection timeout Reintentar manualmente." ↓ Sheets: registrar en log de errores
🔁 Auto-retry — reintentar automáticamente

n8n permite configurar reintentos automáticos por nodo. Si la API falla, espera X segundos y vuelve a intentar antes de declararlo error.

// Configuración en el nodo HTTP Request On Error: "Retry" Max retries: 3 Wait between: 5 segundos // Secuencia: Intento 1 → falla → espera 5s Intento 2 → falla → espera 5s Intento 3 → falla → espera 5s Intento 4 → falla → Error real → dispara Error Trigger
🛤️ Rutas alternativas con "Continue on Error"
// Activar "Continue on Error" en el nodo que puede fallar // El workflow no se detiene — continúa por la rama de error HTTP Request (buscar cliente en CRM) ↓ éxito: datos del cliente ↓ error: objeto de error → { error: "Not found" } // Luego un IF detecta si hubo error: IF error no está vacío → true: crear cliente nuevo en CRM → continuar → false: usar datos existentes → continuar // El workflow termina en ambos casos sin romperse
📋 Los 4 tipos de error en n8n y cómo manejarlos
🌐
API externa caída / timeout — usar auto-retry (3 intentos). Si persiste, notificar por Slack y registrar en log. No detener el workflow completo.
📦
Datos mal formados — usar Filter antes de la acción crítica. Descartar items inválidos silenciosamente o derivarlos a una cola de revisión manual.
🔑
Credencial expirada — n8n notifica en la UI. Configura el Error Trigger para enviar alerta cuando ocurre, con el nombre del workflow afectado.
📬
Acción fallida (email, Slack) — usar rutas alternativas. Si Gmail falla, intentar SMTP de respaldo. Siempre tener un canal secundario para notificaciones críticas.

Wait / Retry

Workflows que esperan, pausan y se reactivan. Para secuencias con tiempo entre pasos, seguimientos automáticos y procesos que dependen de confirmación externa.

⏳
Wait · Pause · Resume · Time-based logic
El workflow puede pausar y retomar
El nodo Wait pausa la ejecución por un tiempo determinado o hasta recibir una señal externa. Esto permite construir secuencias temporales: enviar un email, esperar 3 días, verificar si hubo respuesta, actuar según el resultado. Todo automatizado, sin cron separado.
⏱️ Esperar X tiempo 📅 Hasta fecha/hora 🔔 Hasta webhook 📧 Secuencias de email 🔁 Follow-up automático
⚙️ Modos del nodo Wait
// Modo 1: Esperar tiempo fijo Tipo: "Time Interval" Esperar: 3 días → el workflow se pausa 72 horas y retoma // Modo 2: Esperar hasta fecha/hora específica Tipo: "Specific Time" Hasta: {{$json.fecha_entrega}} → retoma exactamente en esa fecha // Modo 3: Esperar señal externa (webhook) Tipo: "On Webhook Call" URL: generada por n8n automáticamente → pausa indefinidamente hasta que alguien llame esa URL (aprobación manual)
🏢 Casos reales con Wait
📧
Secuencia de onboarding: día 0 bienvenida → Wait 2 días → día 2 tips de uso → Wait 5 días → día 7 invitar a llamada
🔔
Follow-up a lead: formulario → email inmediato → Wait 3 días → IF no respondió: email follow-up → Wait 7 días → tercer toque
✅
Aprobación humana: solicitud de gasto → notifica al gerente → Wait webhook → gerente aprueba/rechaza → continúa flujo
⏰
Recordatorio de cita: cita agendada → Wait hasta 24h antes → enviar recordatorio WhatsApp

Lógica 7 de 8

Sub-workflows

Modularidad real. En vez de un workflow gigante que hace todo, divides la lógica en piezas reutilizables que se llaman entre sí. Como funciones en programación.

📦
Sub-workflows · Execute Workflow · Modularidad
Workflows que llaman a otros workflows
El nodo "Execute Workflow" permite llamar a otro workflow desde el actual, pasarle datos y recibir el resultado. Esto permite crear "funciones reutilizables": un workflow de "enviar notificación" que todos los demás workflows llaman. Cambia la lógica en un solo lugar y actualiza todos.
🔗 Llama otro workflow 📤 Pasa datos 📥 Recibe resultado ♻️ Reutilizable 🧹 Workflows limpios
⚙️ Cómo funciona
// Workflow principal: "Procesar Lead" Webhook → Set → IF válido → Execute Workflow: "Notificar Equipo" pasa: { nombre, email, fuente } → Execute Workflow: "Crear en CRM" pasa: { nombre, email, telefono } ───────────────────────────────── // Sub-workflow: "Notificar Equipo" When Called By Another Workflow recibe: { nombre, email, fuente } ↓ Set → construir mensaje ↓ Slack → canal #leads ↓ Telegram → grupo ventas ↓ retorna: { notificado: true } // Este sub-workflow lo usan // TODOS los workflows que necesiten notificar
💡 Por qué usar sub-workflows
  • ✓
    DRY — Don't Repeat Yourself
    La lógica de notificación está en un solo lugar. Si cambia el canal, editas 1 sub-workflow, no 15 workflows distintos.
  • ✓
    Flujos más cortos y legibles
    El workflow principal tiene 10 nodos claros en vez de 40 nodos mezclados. Más fácil de debugear.
  • ✓
    Testing independiente
    Puedes probar el sub-workflow de notificaciones solo, sin ejecutar todo el flujo principal.
  • ✓
    Colaboración
    Cada persona del equipo puede trabajar en su sub-workflow sin afectar los demás.
🏗️ Arquitectura de sub-workflows en empresa real
// Nivel 1 — Workflows principales (1 por proceso de negocio) 📋 Procesar-Lead → llama a Notificar + Crear-CRM 💳 Procesar-Pago → llama a Notificar + Activar-Cuenta + Factura 📦 Procesar-Pedido → llama a Notificar + Stock + Logística 🚨 Manejar-Error → llama a Notificar + Log-Error // Nivel 2 — Sub-workflows reutilizables 📣 Notificar ← lo llaman TODOS los workflows 📝 Log-Actividad ← registro de todo en Sheets 🧾 Generar-Factura ← lo llaman pago y pedido 📊 Actualizar-Dashboard ← lo llama todo lo que modifica datos

🏗️ Patrón 1 — Pipeline de captación de leads con validación completa
Webhook → validar → clasificar → CRM → notificar equipo → secuencia de emails
WEBHOOK recibe lead del formulario ↓ Filter: email válido AND nombre no vacío AND país no vacío → items inválidos: descartados (no llegan a CRM) ↓ Set: formatear datos + timestamp + calcular score score = {{$json.empresa ? 30 : 0}} + {{$json.telefono ? 20 : 0}} + 50 ↓ Switch: por score del lead → score >= 80: Lead calificado → Execute: "Notificar-Ventas" urgente → score 50-79: Lead interesante → Execute: "Notificar-Ventas" normal → score < 50: Lead frío → solo registro, sin alerta ↓ (todos) HTTP Request: crear contacto en CRM → On error: Continue + log en Sheets "CRM falló" ↓ Execute Workflow: "Secuencia-Onboarding" → Día 0: email bienvenida → Wait 2 días → Día 2: email de valor → Wait 5 días → Día 7: invitar a llamada
🏗️ Patrón 2 — Procesamiento de pedido con manejo de errores robusto
Cada paso protegido. Si algo falla, el cliente sabe y el equipo también.
WEBHOOK recibe pedido de Shopify ↓ Set: extraer campos necesarios con expresiones total = {{$json.line_items.reduce((a,i) => a + i.price, 0)}} es_vip = {{$json.customer.orders_count > 5}} ↓ HTTP Request: verificar stock en ERP (On Error: Continue) IF error no vacío: → Slack "⚠️ ERP no disponible, pedido manual: {{id}}" → Gmail cliente: "procesando tu pedido" (no mencionar el error) IF stock < cantidad_pedida: → Gmail cliente: "producto agotado, opciones alternativas" → STOP ↓ Switch: tipo de envío → "bogota-express" → transportadora A → 4h → "nacional" → transportadora B → 3 días → "internacional" → DHL → calcular arancel ↓ HTTP Request: crear guía (On Error: Retry 3x) → si falla 3x: Slack urgente + pedido en cola manual ↓ Gmail: confirmación con guía + fecha estimada WhatsApp: notificación al cliente (template aprobado) Sheets: registrar pedido con estado "despachado"
🏗️ Patrón 3 — Reporte inteligente con lógica condicional
No solo reporta — compara con la semana anterior y alerta si hay anomalías.
SCHEDULE Lunes 8am ↓ HTTP Request: GET métricas semana actual de Analytics HTTP Request: GET métricas semana anterior (para comparar) ↓ Function: calcular variaciones ventas_delta = (actual.ventas - anterior.ventas) / anterior.ventas * 100 leads_delta = (actual.leads - anterior.leads) / anterior.leads * 100 conversion = (actual.ventas / actual.leads * 100).toFixed(1) ↓ IF: alguna métrica cayó más del 20% → true: Slack urgente "🚨 ALERTA: {{metrica}} cayó {{delta}}%" → false: Slack normal con emoji positivo ↓ (ambas ramas) Set: construir cuerpo del email con expresiones ternarias tendencia = {{ventas_delta > 0 ? '📈 +' : '📉 '}}{{ventas_delta.toFixed(1)}}% ↓ Gmail: reporte HTML semanal al cliente/gerencia Sheets: registrar métricas históricas (para el próximo lunes comparar)
